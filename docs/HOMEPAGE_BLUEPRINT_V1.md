## 1. 한 문장 정의

로앤 홈페이지는 법률사무소 소개서가 아니라, 빚 문제로 불안한 사람이 **이해 → 상황 정리
→ 신뢰 형성 → 적절한 상담**으로 이동하고, 계약 후에는 리걸프렌즈로 안전하게 이어지는
**고객 여정의 프런트 도어**다.

홈페이지가 잘 작동한다는 것은 문의 수만 많다는 뜻이 아니다. 다음 네 가지가 동시에
성립해야 한다.

1. 방문자가 자신의 선택지를 과장 없이 이해한다.
2. 상담자가 필요한 맥락을 이미 받은 상태로 사람 상담을 시작한다.
3. 상담·계약 정보가 ERP를 거쳐 리걸플로·리걸프렌즈로 중복 입력 없이 이어진다.
4. 광고·콘텐츠·상담·사건 결과가 개인정보를 침해하지 않는 범위에서 다시 개선에 쓰인다.

이 제품의 분위기는 **“다급함을 자극하는 법률 광고”가 아니라 “복잡한 상황을 차분히
정리해 주는 회복 서비스”**로 정한다.

## 2. 이번 설계에서 확정하는 것과 출시 전 게이트

### 2-1. 제품 기준선으로 확정

- 모바일을 축소된 데스크톱이 아니라 **주요 제품 화면**으로 설계한다.
- 공개 정보 → 익명 상황 정리 → 상담 요청 → 계약 후 리걸프렌즈 인계를 하나의 연속된
  여정으로 만든다.
- 모든 공개 정보에는 작성자·검토 변호사·근거·검토일을 표시한다.
- 상담 전에는 필요한 최소 정보만 받고, 상세 채무·서류는 인증된 공간에서 받는다.
- ERP를 고객·상담·사건 상태의 단일 진실원천으로 삼는다.
- AdPilot에는 광고 성과에 필요한 가명·집계 데이터만 보내고 사건 상세나 원문 개인정보를
  보내지 않는다.
- AI는 우선 내부 직원의 요약·분류·질문 제안·문서 처리와 변호사 검토형 콘텐츠 제작에
  사용한다. 판단과 발행은 사람이 책임진다.
- 현재 운영 중인 `lawandfirm.com`의 기존 본문은 참고자료로만 사용하고, 공식 1차 자료와
  로앤의 원본 해설을 바탕으로 다시 작성한다. 전체 URL 대응표는 첫 구현의 선행 조건으로
  두지 않되 실제 검색 유입·외부 링크가 있는 핵심 URL은 출시 전 유지하거나 단일 301한다.
- 기존 개인회생·파산 고객후기는 원문성과 작성 맥락을 보존해 전량 이관하고, 개인정보·
  삭제 상태·광고 표현을 검수한 뒤 공개한다.
- 홈페이지 자체 회원가입·고객 포털은 초기 범위에서 제외하고 계약 후 고객 접점은
  리걸프렌즈가 담당한다.

### 2-2. 출시 전에 반드시 통과해야 하는 법률·운영 게이트

대한변호사협회의 2025년 6월 30일 개정 「변호사 광고에 관한 규칙」은 광고에서 소비자가
인공지능 등 프로그램을 직접 사용하거나 그런 프로그램으로 연결하는 방식을 제한한다.
「변호사 광고에 관한 규정」에는 인공지능을 광고에 이용할 때의 등록·검토 변호사 표시
요건도 있다. 따라서 홈페이지가 광고에 해당하는 범위에서는 다음 원칙을 적용한다.

- **공개 LLM 법률상담 챗봇은 v1 출시 범위에서 제외**한다.
- 단계형 자가진단·변제금 계산기도 명칭을 바꾸는 것만으로 안전하다고 전제하지 않는다.
  결정형 규칙 엔진을 쓰더라도 공개 전에 책임 변호사와 대한변협 광고 규정 관점의 별도
  심사를 받는다.
- 공개 도구의 출력은 자격 확정, 성공 가능성, 예상 탕감률이나 사건 결과가 아니라
  사용자가 입력한 사실의 요약, 확인할 쟁점, 부족한 정보, 다음 행동으로 제한한다.
- 수임 후 리걸프렌즈에서 고객이 직접 쓰는 AI 기능도 “광고가 아니므로 괜찮다”고
  추정하지 않고 서비스 성격·개인정보·전문직 책임을 별도로 검토한다.
- 광고별 광고 주체와 책임 변호사, 콘텐츠별 검토자를 표시한다.

그 밖에도 성공 보장·결과 예측·최고/유일·과도한 비교·최저가·부당한 무료·할인·환불·
후불 강조와 같은 표현은 사용하지 않는다. 비용 정보는 실제 계약 조건과 서비스 범위를
투명하게 설명하되, 비교·유인성 문구는 책임 변호사의 사전 검토를 거친다.

> 이 문서는 제품 설계안이지 법률의견서가 아니다. 공개 도구, 카피, 사례, 비용 표현은
> 출시 전 책임 변호사 검토와 필요 시 대한변협 사전 확인을 거친다.

## 3. 고객 생애주기와 홈페이지의 역할

| 단계 | 고객이 실제로 묻는 것 | 홈페이지가 해야 할 일 | 시스템 연결 |
|---|---|---|---|
| 발견 | “독촉이 시작됐는데 어떻게 하지?” | 검색 의도에 정확히 답하고 안전한 첫 행동 제시 | AdPilot 유입 정보, 콘텐츠 분석 |
| 이해 | “회생과 파산 중 무엇을 봐야 하지?” | 쉬운 비교, 절차·기간·자료·생활 영향 설명 | 콘텐츠 지식베이스 |
| 상황 정리 | “내 조건에서는 무엇을 확인해야 하지?” | 익명 단계형 질문, 입력 요약, 쟁점·다음 행동 | 홈페이지 세션, 버전형 규칙 |
| 신뢰 형성 | “이곳이 내 상황을 제대로 다룰까?” | 검증 가능한 변호사·사무소 정보와 유사 사례 | 승인된 공개 사례 저장소 |
| 상담 요청 | “무엇을 말해야 하고 언제 연락오나?” | 최소 입력, 선호 채널·시간, 상태가 보이는 접수 | gateway → ERP |
| 사람 상담 | “내 말을 다시 처음부터 해야 하나?” | 동의받은 입력을 상담자에게 안전하게 인계 | ERP, 내부 AI 상담 보조 |
| 계약·사건 | “지금 무엇을 해야 하고 어디까지 됐나?” | 리걸프렌즈로 명확히 인계 | ERP, 리걸플로, 리걸프렌즈 |
| 종결·면책 | “이제 어떤 기록을 보관하고 무엇을 조심하나?” | 공개 회복 정보 제공, 개별 정보는 리걸프렌즈 | 리걸프렌즈, ERP 종결 이벤트 |
| 사후관리 | “새 출발을 유지하려면?” | 공개 최신 안내의 검색 접점 | 리걸프렌즈, Aftercare 에이전트 |

핵심은 단계가 바뀌어도 고객에게 같은 질문을 반복하지 않는 것이다. 홈페이지에서 정리한
내용은 동의와 목적 범위 안에서 ERP의 상담 카드로 이어지고, 계약 고객은 동일한 브랜드
경험 안에서 리걸프렌즈로 이동한다. 홈페이지 사용을 위해 별도 계정을 만들게 하지 않는다.

## 4. 리서치에서 가져온 설계 원칙

이번 초안은 법률 서비스만 보지 않고 채무 상담, 정부 서비스, 사건 공유 앱, 온라인 법률
플랫폼의 대표 패턴을 비교했다. 해외 제도와 국내 법률은 다르므로 **법률 내용은 가져오지
않고 상호작용 원칙만 채택**한다.

| 서비스·패턴 | 배울 점 | 로앤에 적용 | 그대로 복제하지 않을 것 |
|---|---|---|---|
| 현재 로앤 `/bank` | 회생·파산 정보, 절차, 서류, FAQ, 사례, 기존 자가진단 자산 | 기존 URL·콘텐츠·진단 로직을 전수 조사해 재사용 | 낡은 WordPress 구조, 이미지맵, 중복 스크립트 |
| 국내 회생·파산 랜딩 사례 | 짧은 상황 확인, 명확한 단계, 상황별 진입점 | 첫 화면에서 한 질문으로 시작, 6단계 내외 진행 | 최대 감면 수치, 결과 암시, 과도한 긴급성 |
| Upsolve | 쉬운 말의 단계형 질문, 왜 묻는지 설명, 사용자가 통제 | 한 화면 한 질문, 뒤로가기, 입력 검토 | 미국 파산 자격 로직과 자동 문서 기능 |
| StepChange | 비판하지 않는 어조, 저장·재개, 선택지 비교, 압박 없는 다음 단계 | 익명 시작, 나중에 이어하기, 상담 외 선택지도 설명 | 영국 채무 제도와 “무료” 표현의 단순 이식 |
| GOV.UK 서비스 패턴 | 한 페이지 한 질문, 모름 선택, 답변 확인 | 진단·상담 폼의 기본 상호작용 규칙 | 정부 서비스처럼 보이게 하는 시각·문구 |
| Clio for Clients | 사건 중심 메시지·서류·일정·청구, 모바일 문서 촬영 | 리걸프렌즈 인계 품질을 평가할 참조 기준 | 홈페이지에 중복 고객 포털 구축 |
| Rocket Lawyer·LegalZoom | 셀프서비스에서 전문가에게 맥락을 잃지 않고 인계 | 정보 탐색 결과와 상담 요청을 연결 | 공개 생성형 AI의 직접 상담 |
| Google·네이버 검색 가이드 | 사람에게 유용한 원본 콘텐츠, 모바일 동등성, 명확한 출처 | 변호사 검토 콘텐츠·공식 근거·원본 사례·서버 렌더링 | 대량 AI 문서, 얇은 지역·키워드 페이지 |

### 설계 원칙 여섯 가지

1. **차분함:** 수치심·공포·조급함을 전환 장치로 쓰지 않는다.
2. **선택권:** 상담을 강요하지 않고 읽기, 상황 정리, 사람 상담 중 다음 행동을 고르게 한다.
3. **정직한 불확실성:** 모르는 것은 모른다고 말하고, 판단에 필요한 추가 사실을 보여준다.
4. **연속성:** 로그인 전 입력도 사용자의 동의 아래 상담과 포털로 이어지게 한다.
5. **증거:** 모든 중요한 설명은 공식 근거, 검토자, 갱신일, 실제 운영 사실로 뒷받침한다.
6. **최소수집:** “나중에 쓸지 모르는 정보”를 미리 받지 않는다.

## 5. 현재 홈페이지 진단과 이전 원칙

2026-07-24 기준으로 `lawandfirm.com`과 `lawandfirm.com/bank/`를 관찰한 결과다. 구현 전에
크롤링과 Search Console·네이버 서치어드바이저 데이터를 더해 확정한다.

### 보존할 자산

- 이미 검색 엔진과 외부 링크가 알고 있는 도메인과 URL
- 개인회생·파산의 절차, 자격, 필요 서류, FAQ, 판례, 성공 사례 콘텐츠
- 부양가족·소득·채무·재산 범위를 묻는 기존 자가진단의 질문 경험과 운영 노하우
- 서울·대전·부산 사무소의 실제 정보와 축적된 상담 의도 데이터
- 전화·카카오·1:1 상담 등 사용자가 익숙한 접점

### 개선할 문제

- WordPress 4.7.2 표기, 여러 버전의 jQuery와 다수 CSS·JS가 섞인 오래된 전달 구조
- 공개 정보 페이지까지 세션 쿠키와 `no-store/no-cache`가 적용되는 비효율
- 이미지맵 중심의 일부 상호작용과 키보드 포커스 제거 등 접근성 문제
- 확인 시점에 `/sitemap.xml`이 404였고, 구조화 데이터가 관찰되지 않은 검색 기반 문제
- 모바일 첫 화면에서 정보보다 전환 장치가 경쟁하는 구조
- 공개 사례와 자가진단의 개인정보·사례 승인·법률광고 규정 준수 상태를 새 기준으로
  재검증해야 하는 문제

### 이전 원칙

1. 기존 본문은 정보 출처가 아니라 주제 누락을 확인하는 참고자료로만 사용한다.
2. 새 본문은 법원·법령 등 최신 1차 자료와 로앤 변호사의 원본 해설로 다시 작성한다.
3. Search Console·백링크에서 가치가 확인된 핵심 URL만 **유지 / 단일 301**을 결정한다.
4. 301은 가장 가까운 새 문서로 한 번만 연결하고 연쇄 리다이렉트를 만들지 않는다.
5. 새 페이지의 제목·본문·canonical·내부 링크·사이트맵을 한 묶음으로 검증한다.
6. 출시 전후 8주 이상 404, 색인, 순위, 전환을 비교한다.

정식 도메인은 기존 검색 자산이 있는 `lawandfirm.com`으로 확정했다. `lawand.co.kr`은
본 사이트의 canonical 도메인으로 사용하지 않으며, 두 도메인을 동시에 색인 가능한
본 사이트로 운영하지 않는다.

## 6. 고객 상태와 진입 의도

연령·성별 같은 고정 인구통계보다 **지금 어떤 질문과 긴급도를 가진 사람인가**로 화면을
설계한다.

| 상태 | 대표 질문 | 첫 화면의 최적 행동 |
|---|---|---|
| 즉시 대응 필요 | 급여·계좌 압류, 독촉, 소송·경매가 임박했나 | 긴급 상황별 정보 → 사람 상담 요청 |
| 자격 탐색 | 소득은 있지만 빚을 감당하기 어렵다 | 개인회생 조건 이해 → 상황 정리 |
| 선택지 비교 | 회생과 파산 중 무엇이 다른가 | 비교표 → 내 조건에서 확인할 쟁점 |
| 생활 영향 확인 | 가족·회사에 알려지는가, 카드·통장은 어떻게 되나 | 생활 주제별 가이드 |
| 신뢰 검증 | 비용·기간·누가 맡는지·비슷한 사례가 있나 | 변호사·과정·승인 사례 |
| 재방문 상담자 | 전에 입력한 내용을 이어가고 싶다 | 안전한 이어하기 → 접수 상태 |
| 사건 고객 | 서류·기일·현재 단계가 궁금하다 | 리걸프렌즈로 이동 |
| 종결 고객 | 면책 이후 기록·신용·후속 조치가 궁금하다 | 사후관리 체크리스트 |

지역·직업·채무 원인별 페이지는 사용자의 실제 질문과 고유한 답변이 있을 때만 만든다.
키워드만 바꾼 대량 지역 페이지나 직업별 얇은 문서는 만들지 않는다.

### 전역 내비게이션

모바일 상단에는 로고, `상담 요청`, `메뉴`만 둔다. 메뉴를 열면 아래 순서로 보인다.

1. 개인회생
2. 개인파산·면책
3. 회생·파산 비교
4. 사례로 이해하기
5. 절차·서류·생활 안내
6. 로앤과 변호사
7. 상담 요청

전화는 화면 아래의 고정 행동 영역에서 제공하되 `상담 요청`과 동등한 선택지로 둔다.
데스크톱은 상단에 분야·후기·사례·가이드·로앤 소개를 두고 우측에 상담 요청 버튼을
둔다. 계약 고객의 리걸프렌즈 이동은 메뉴의 보조 링크로 제공한다. 드롭다운은 두 단계
이상 깊어지지 않는다.

자동 재생 영상, 자동 회전 캐러셀, 사용자를 따라다니는 챗봇 말풍선은 사용하지 않는다.

### 8-2. 데스크톱 구성

- 최대 본문 폭 1,200px, 12열 그리드
- 히어로 좌측 7열: 메시지·행동, 우측 5열: 상황 정리 첫 질문
- 의도 카드는 3열 2행, 비교와 사례는 2단 분할
- 긴 본문은 한 줄 65~75자 수준으로 제한
- 상담 CTA는 섹션 사이에 반복하되 같은 문구를 과도하게 반복하지 않는다.
- 우측 고정 퀵 메뉴 대신 본문 문맥 안에 다음 행동을 둔다.

### 8-3. 첫 화면 카피 원칙

초안 헤드라인:

> 빚의 크기보다, 지금의 조건부터 봅니다.

초안 설명:

> 소득·재산·채무와 현재 상황을 차분히 정리하고, 변호사가 확인할 쟁점과 다음 단계를
> 안내합니다.

버튼:

- 기본: `내 상황 정리 시작`
- 보조: `사람에게 상담 요청`
- 탐색: `입력 없이 먼저 알아보기`

출시 전 광고 심사를 전제로 한 초안이다. `무조건`, `즉시 해결`, `성공`, `최대 탕감`,
`전국 1위`, `유일`, 근거 없는 처리 건수, 실제 운영이 보장되지 않는 연락 시간은 쓰지
않는다.

## 9. 핵심 페이지 상세 설계

### 9-1. 상황 정리 도구

목적은 자동 판정이 아니라 **상담 전에 사실을 빠짐없이 정리하고 사용자가 쟁점을
이해하도록 돕는 것**이다.

#### 상호작용

- 로그인·이름·전화번호 없이 시작한다.
- 한 화면에 한 질문만 보여준다.
- 모든 질문에 `잘 모르겠어요`와 `왜 묻나요?`를 제공한다.
- 이전 답변으로 돌아갈 수 있고, 예상 질문 수와 진행률을 표시한다.
- 질문은 가능하면 6~8개 핵심 분기로 제한한다.
- 기본 저장은 브라우저 세션 범위로 하고, 명시적으로 이어하기를 선택할 때만 안전한
  복구 수단을 제공한다.
- 입력 도중 전화번호를 요구하지 않는다.

#### 질문 범주

1. 급여·사업 등 정기 소득 유무와 안정성
2. 채무의 대략적 범위와 주요 종류
3. 재산의 대략적 범위와 담보 여부
4. 부양 상황
5. 연체·독촉·소송·압류의 현재 단계
6. 최근 재산 처분·특정 채권자 변제 등 추가 확인이 필요한 사실
7. 거주 지역과 관할 확인
8. 사용자가 가장 걱정하는 생활 영향

#### 결과 화면

```text
당신이 입력한 상황
 └ 소득·채무·재산·긴급 상황을 범위로 요약

변호사가 우선 확인할 3가지
 ├ 정기 소득과 변제 지속 가능성
 ├ 담보채무·재산의 구체적 구성
 └ 압류·소송 일정

현재 정보만으로 확정할 수 없는 것
 └ 필요한 추가 사실과 이유

다음에 할 수 있는 일
 ├ 관련 제도 비교 읽기
 ├ 준비 자료 체크리스트 받기
 └ 이 내용을 붙여 사람 상담 요청하기

비슷한 공개 사례
 └ 공통점과 중요한 차이를 함께 표시
```

`개인회생 가능 87%`, `예상 탕감 80%`, `파산 확정`과 같은 출력은 하지 않는다. 규칙과
설명은 버전 관리하고, 근거 출처·검토 변호사·검토일을 표시한다. 긴급 위험을 감지해도
공포 문구 대신 **확인해야 할 기한과 즉시 연결할 사람 상담 경로**를 보여준다.

### 9-2. 변제 계획 이해 도구

- 단일 숫자가 아니라 입력 가정에 따른 **범위와 시나리오**를 보여준다.
- 계산식의 입력값·가정·제외 항목을 바로 확인할 수 있게 한다.
- 실제 인정 생계비·가용소득·재산·법원 판단에 따라 달라질 수 있음을 구체적으로 설명한다.
- 결과보다 `어떤 값이 결과를 바꾸는가`를 시각화한다.
- 입력을 URL, 분석 도구, 오류 로그에 싣지 않는다.
- 상황 정리 도구와 마찬가지로 공개 전 광고 규정 검토를 받는다.

### 9-3. 개인회생·파산 비교 페이지

첫 화면에 결론을 강요하는 퀴즈 대신 아래 축으로 나란히 비교한다.

- 기본 취지
- 소득과 변제
- 재산과 채무
- 절차의 큰 단계
- 생활에 미칠 수 있는 영향
- 추가로 확인할 예외
- 공식 법원 안내

표 아래에는 `어느 쪽이 더 좋다`가 아니라 `내 상황에서 무엇을 더 확인해야 하는가`를
보여준다. 모바일에서는 가로 스크롤 표 대신 비교 항목 하나씩 두 제도를 세로로 배치한다.

### 9-4. 공개 사례 탐색

사례는 전환 장식이 아니라 낯선 절차를 실제 맥락으로 이해하는 학습 도구다.

#### 카드에 보일 정보

- 상황 제목: 결과가 아니라 출발 상황 중심
- 소득·채무·재산·가구 정보를 넓은 구간으로 표시
- 핵심 쟁점 1~2개
- 선택한 절차와 주요 진행 단계
- 결과가 나온 시기와 검토일
- `내 사건과 다를 수 있는 핵심 차이`

#### 공개 데이터 정책

- 운영 DB의 사건을 그대로 검색하게 하지 않는다.
- 별도의 `public_approved` 사례 읽기 모델을 만든다.
- 당사자 동의 또는 적법한 공개 근거, 고객 불이익 여부, 익명화 검토, 책임 변호사 승인을
  모두 기록한다.
- 정확한 생년월일, 동네, 직장, 날짜, 가족 조합, 특이 사건 경위는 제거·범주화한다.
- 익명화 버전과 승인 이력을 보존한다.
- 필터 조합으로 한 사람을 유추할 수 없도록 최소 노출 집단 기준을 운영한다. 이 기준은
  법적 면책 기준이 아니라 추가적인 위험 완화 장치다.
- 사례 결과는 미래 결과를 보장하지 않는다는 설명을 문맥 안에 둔다.

개별 사례는 `출발 상황 → 쟁점 → 확인 과정 → 절차 → 결과 → 다른 사건에서 달라질 수
있는 점` 순으로 쓴다. “성공 사례”보다 `사례로 이해하기`를 기본 명칭으로 사용한다.

내부 사건의 공개 사례화는 `ERP 사건 단계 이벤트 → 후보 추출 → 최소 필드 복사 →
동의·공개 근거 확인 → 익명화·범주화 → AI 초안 → 개인정보 검수 → 책임 변호사 승인 →
예약 발행 → 정기 재검토·철회` 흐름으로 계속 운영한다. AI 초안은 자동 게시하지 않는다.

### 9-4-1. 고객후기

기존 개인회생·파산 고객후기는 반드시 전량 이관한다. 원문·작성일·익명 작성자·분야·
작성 당시 진행단계·태그·원본 ID를 보존하고, 전화·주소·계좌·사건번호 등 개인정보와
삭제·비공개 상태를 검수한다. 원문을 미화하지 않으며 PII를 가린 경우 편집 사실을
표시한다. 후기의 결과가 다른 사건의 결과를 보장하지 않는다는 설명을 가까이 둔다.

후기 허브는 분야·진행단계·작성시기별 탐색을 제공하되 필터 조합을 무분별하게
색인시키지 않는다. 짧은 후기마다 색인용 페이지를 대량 생성하지 않고 기존 검색 성과와
외부 링크를 기준으로 고유 페이지 유지 또는 목록 위치로의 301을 결정한다. 상세 이관
규칙은 [`SEO_CONTENT_MIGRATION_V1.md`](SEO_CONTENT_MIGRATION_V1.md)를 따른다.

### 9-5. 상담 요청

상담 폼은 짧되, 제출 후 사람이 일할 수 있을 만큼 구조화한다.

1. **연락 방법:** 전화·문자 등 실제 운영 가능한 채널, 연락 가능한 시간, 지역
2. **상황:** 상황 정리 결과를 불러오거나 300자 내외로 직접 입력
3. **확인:** 입력 내용, 필수 개인정보 동의, 선택적 마케팅 동의를 분리해 검토

이름은 첫 접수에 반드시 필요하지 않다면 선택으로 두고, 전화번호 등 연락 식별자는
상담을 요청하는 마지막 단계에서만 받는다. 제출 후에는 다음을 제공한다.

- 접수번호
- 어떤 팀이 어떤 채널로 연락하는지
- 실제 운영으로 지킬 수 있는 예상 연락 범위
- 입력 수정·상담 취소 방법
- 긴급한 법원·집행 기한이 있다면 기다리지 않고 확인할 공식 경로

상황 정리를 먼저 한 사용자는 답을 다시 입력하지 않는다. URL 파라미터가 아니라
서버 측 단기 참조 토큰으로 연결한다.

### 9-6. 변호사·신뢰 페이지

사용자가 검증할 수 있는 사실만 쓴다.

- 성명, 사진, 변호사 등록·실제 경력, 담당 역할
- 대한변협 등록 전문분야가 있는 경우에만 정확한 명칭 사용
- 직접 작성·검토한 콘텐츠
- 사무소별 실제 주소·연락·접근성 정보
- 로앤의 상담 인계·서류 검토·사건 관리 방식
- 홈페이지 광고 주체와 책임 변호사

스톡 법정·법봉·악수 사진, 근거 없는 배지, 의미가 불분명한 누적 수치로 신뢰를 대신하지
않는다.

### 9-7. 가이드·해설 문서 템플릿

모든 주요 콘텐츠는 아래 순서를 기본으로 한다.

1. 3~5문장의 직접 답변
2. 이 설명이 적용되는 범위
3. 기본 원칙과 중요한 예외
4. 실제 상황 예시
5. 지금 준비할 것과 다음 행동
6. 자주 묻는 후속 질문
7. 공식 근거와 참고 자료
8. 작성자·검토 변호사·최초 작성일·최근 검토일·변경 이력

법령을 길게 복사하지 않고 쉬운 말로 설명한 뒤 공식 원문으로 연결한다. 같은 검색어를
겨냥한 유사 문서를 여러 개 만들기보다 하나의 강한 문서와 관련 질문 허브를 만든다.

### 9-8. 계약 후 리걸프렌즈 인계

홈페이지에는 별도 회원가입이나 `내 사건` 포털을 만들지 않는다. 상담·계약 상태가
확인되면 ERP 이벤트를 통해 리걸프렌즈 초대와 사건 인계가 이어진다. 홈페이지에는
리걸프렌즈 이동 링크, 설치·접속 안내, 계정 문제 지원 연락처만 제공한다.

## 10. 시각 디자인 시스템

### 10-1. 디자인 방향: 조용한 확신

금색·검정색·법봉·법원 기둥으로 권위를 과시하는 전형적인 법률 광고에서 벗어난다.
금융 회복 서비스와 잘 정돈된 공공 서비스의 명료함에, 실제 로앤 구성원의 온기를 더한다.
브랜드의 넓은 면은 아이보리와 잉크가 맡고, 초록색은 버튼·링크·체크·진행 상태처럼
사용자의 다음 행동을 알려주는 신호색으로만 사용한다. 로앤을 “그린 법무법인”으로
인식시키는 것이 목표가 아니다.

### 10-2. 색상

| 토큰 | 색상 | 용도 | 흰색 배경 대비 |
|---|---:|---|---:|
| `ink` | `#181E1C` | 본문·제목 | 16.92:1 |
| `ink-900` | `#171D1B` | 비교·후기·상담의 짙은 배경 | 17.10:1 |
| `action-600` | `#276A57` | 기본 버튼·링크·상태 신호 | 6.39:1 |
| `signal-050` | `#EEF5F1` | 체크·태그 주변의 제한적 배경 | 장식 배경 전용 |
| `ivory-050` | `#F7F3EA` | 주요 넓은 배경 | 장식 배경 전용 |
| `paper` | `#FFFDF8` | 카드·본문 배경 | 장식 배경 전용 |
| `slate-600` | `#5D6863` | 보조 본문 | 5.79:1 |
| `amber-700` | `#8A551D` | 주의·기한 | 6.18:1 |
| `danger-700` | `#A33A32` | 오류·위험 | 6.54:1 |

아이보리와 종이색을 기본으로 하고 잉크를 제목·넓은 짙은 면에 사용한다. 초록색은 행동과
진행 상태에만 절제해 사용한다. 색상만으로 상태를 구분하지 않고 아이콘·문구를 함께 둔다.

### 10-3. 글꼴과 크기

- 한국어 본문은 로컬 호스팅한 단일 산세리프 가변 글꼴을 우선한다. 후보는 Pretendard
  또는 SUIT이며 실제 기기 렌더링과 라이선스 확인 후 하나만 채택한다.
- 모바일 본문 17px, 줄높이 1.65
- 모바일 H1 32px/1.2, 데스크톱 H1 52px/1.12
- H2 26~32px, H3 21~24px
- 보조 정보도 14px 미만으로 내리지 않는다.
- 숫자는 표에서 비교하기 쉽도록 tabular figures를 쓴다.

### 10-4. 간격과 구성요소

- 8px 간격 체계, 모바일 좌우 여백 20px
- 기본 버튼 높이 52px, 최소 터치 영역 48×48px
- 카드 반경 16px, 입력 필드 12px, 그림자는 매우 옅게 사용
- 입력 라벨은 필드 안 placeholder로 대체하지 않는다.
- 포커스 링은 3px 이상 명확히 보이게 한다.
- 오류는 상단 요약과 해당 필드 바로 아래에 함께 표시한다.
- 모션은 160~220ms 이내로 제한하고 `prefers-reduced-motion`을 존중한다.

### 10-5. 사진과 그래픽

- 실제 변호사·상담자·사무소를 자연광과 중립 배경에서 촬영한다.
- 고객 재연 사진으로 공포·절망을 연출하지 않는다.
- 채무·소득·절차는 장식 일러스트보다 이해 가능한 도표와 타임라인으로 표현한다.
- SVG 아이콘은 한 선 굵기와 둥근 모서리 체계를 사용한다.
- 핵심 이미지는 의미 있는 대체 텍스트를 제공하고 장식 이미지는 보조기기에서 숨긴다.

## 11. AI의 역할과 경계

### 11-1. v1에서 사용하는 AI

| 영역 | AI가 하는 일 | 사람이 하는 일 |
|---|---|---|
| 콘텐츠 운영 | 공식 출처 검색 보조, 초안·FAQ 후보·변경점 비교 | 사실 확인, 법률·광고 검토, 승인·발행 |
| 상담 준비 | 입력 요약, 긴급 쟁점·누락 질문·유사 내부 사례 후보 | 실제 질문, 법률 판단, 상담·계약 |
| 통화 보조 | 동의된 STT, 실시간 쟁점·확인 질문 제안 | 통화 진행, 제안 채택 여부, 기록 확정 |
| 사건 운영 | OCR, 문서 분류, 누락 탐지, 초안 요약 | 원문 대조, 제출 판단, 최종 승인 |
| 고객 안내 | 사건 상태를 쉬운 말로 바꾼 메시지 초안 | 발송 조건·내용 승인 또는 규칙형 발송 |
| 사후관리 | 종결 유형별 체크인 후보와 질문 분류 | 중요한 문의 응답, 최신성·적합성 검토 |

### 11-2. v1에서 하지 않는 것

- 공개 LLM 법률상담 챗봇
- 사용자의 사건 가능성·성공률·탕감률 자동 예측
- AI가 쓴 법률 콘텐츠의 무검토 자동 발행
- AI가 결정한 상담 거절이나 우선순위의 무검토 실행
- 공개 사례와 내부 사건 DB의 직접 연결
- 모델 제공자에게 목적 밖 학습을 허용하는 원문 개인정보 전송

### 11-3. AI 운영 안전장치

- 과업마다 허용된 데이터 필드와 도구를 명시하고 최소 권한을 적용한다.
- 모델 출력은 타입이 있는 구조화 결과로 받고 근거·불확실성·모델·프롬프트 버전을 남긴다.
- 공식 출처 스냅샷과 답변을 연결하고 최신성 만료일을 둔다.
- 프롬프트 인젝션을 가정해 업로드 문서와 웹 콘텐츠를 신뢰하지 않는다.
- 이름·전화·계좌·주민등록번호 등은 과업에 필요하지 않으면 모델 입력 전에 제거한다.
- 모델이 사람에게 보낼 문구나 사건 상태를 직접 확정하지 못하게 승인 경계를 둔다.
- 고위험 출력, 낮은 신뢰도, 충돌하는 출처는 반드시 사람 검토 큐로 보낸다.
- 고객에게 자동화 사용 여부와 사람에게 이의를 제기할 경로를 이해하기 쉽게 알린다.

## 12. 시스템 연동 설계

### 12-1. 전체 흐름

```text
네이버·구글·ChatGPT·직접 방문
                │
                ▼
      홈페이지: 정보·상황 정리·사례
                │
       consultation.requested
                ▼
     gateway: 검증·중복 방지·이벤트
                │
                ▼
       ERP: 고객·상담 상태의 원장
        │          │             │
        ▼          ▼             ▼
    리걸플로   내부 AI 에이전트   리걸프렌즈
        │       상담·문서 보조      사건 관리
        └──────────┬──────────────┘
                   ▼
        리걸프렌즈 고객 애플리케이션
                   │
          종결·사후관리·만족도
                   │
                   ▼
    AdPilot에는 가명 전환 단계·가치만 환류
```

### 12-2. 시스템별 데이터 책임

| 시스템 | 책임지는 데이터 | 가지면 안 되는 데이터 |
|---|---|---|
| 홈페이지 | 공개 콘텐츠, 익명 세션, UI 상태, 단기 접수 참조 | 사건 원본 전체, 장기 상세 개인정보 |
| gateway | 입력 검증, idempotency, 이벤트 outbox·전달, 웹훅 | 별도 고객 원장 |
| ERP | 연락처, 동의, 상담·고객·사건 상태, 담당자, 운영 이력 | 광고 최적화용 복제 데이터 |
| 리걸플로·리걸프렌즈 | 각 시스템이 책임지는 업무·사건 데이터와 계약 후 고객 공유 | 홈페이지 분석용 원문 로그 |
| AdPilot | click ID, UTM, 익명 방문·실험, 가명 전환 단계·가치 | 이름, 전화 원문, 상담 내용, 채무·재산·건강 정보 |
| AI 에이전트 | 과업별 최소 입력, 출력·검토·버전·감사 기록 | 목적과 무관한 전체 고객 프로필 |
| 공개 사례 저장소 | 승인·익명화된 읽기 전용 사례 | 운영 DB와 실시간 식별 연결 |

### 12-3. 홈페이지 이벤트 카탈로그 초안

정식 스키마는 `packages/core`에서 버전 관리한다.

```text
visitor.session.started
content.viewed
situation_check.started
situation_check.step_completed
situation_check.completed
case_search.performed
public_case.viewed
consultation.requested
consultation.contact_verified
consultation.assigned
consultation.contacted
consultation.completed
engagement.created
case.phase_changed
document.requested
document.uploaded
document.verified
discharge.completed
aftercare.checkin_completed
satisfaction.submitted
```

모든 이벤트는 `event_id`, `event_version`, `occurred_at`, `producer`, `correlation_id`,
`subject_id`의 가명 참조, `consent_context`, `source`를 공통으로 갖는다. 금액·채무·문서
원문 같은 데이터는 기본 이벤트에 넣지 않고 권한 있는 시스템의 레코드를 참조한다.

#### 가장 먼저 구현할 수직 흐름

```text
광고·검색 유입
 → 익명 세션과 first-party attribution 저장
 → 상황 정리 완료
 → 동의 후 상담 요청
 → gateway가 ERP 상담 생성
 → 담당자 배정·연락
 → 수임 여부·수납 단계
 → AdPilot에 가명 전환 단계 환류
```

전화번호는 ERP에서 원문을 관리하고, AdPilot 연계에는 정규화 후 일방향 해시를 사용한다.
시간대만으로 고객을 추정하지 않으며 click ID·UTM·first-party 세션과 동의된 식별자를
조합한다.

### 12-4. 광고 자동화의 경계

AdPilot이 자동으로 바꿔도 되는 것과 책임 변호사 승인이 필요한 것을 분리한다.

- 자동 허용 후보: 예산 배분, 입찰, 승인된 소재 조합, 랜딩 속도 기반 제외
- 사전 승인 필요: 법률적 주장, 결과·비용·전문성 표현, 사례 문구, 진단 결과 카피
- 금지: 채무액·건강·가족·사건 세부를 이용한 개인 타기팅, 공포를 이용한 다크 패턴,
  승인되지 않은 AI 생성 광고의 자동 게시
- 모든 랜딩·실험은 `page_version`, `copy_approval_id`, `experiment_id`를 남긴다.
- 전환율이 높더라도 불만, 잘못된 기대, 부적합 상담, 취소가 늘면 자동으로 승격하지 않는다.

## 13. 개인정보·보안 설계

개인회생·파산 입력은 법률상 모든 항목이 같은 분류의 민감정보라는 뜻은 아니지만, 재산·
채무·소득·건강·가족·소송 정보가 결합되면 매우 높은 재식별·피해 위험을 가진다.

### 수집 단계

- 익명 탐색에는 쿠키 동의를 강요하지 않고 필수 세션만 최소 사용한다.
- 상담에 필요한 수집 목적·항목·보유기간·거부 영향을 제출 직전에 이해하기 쉽게 표시한다.
- 필수 상담 동의와 선택적 광고성 정보 수신 동의를 분리한다.
- 주민등록번호, 계좌, 원본 서류는 일반 상담 폼에서 받지 않는다.
- 마케팅 픽셀에는 폼 입력값·페이지 내 자유 서술·상황 정리 답을 전달하지 않는다.

### 전송·저장·접근

- 브라우저가 ERP DB에 직접 접근하지 않고 gateway의 좁은 API를 사용한다.
- TLS, 저장 암호화, 비밀 관리, 최소 권한 RBAC, 접근·다운로드 감사 로그를 적용한다.
- 상세 재무 입력은 URL, 로컬스토리지, 분석 이벤트, 오류 추적 본문에 남기지 않는다.
- 접수 API는 idempotency, 속도 제한, 봇·스팸 방어, 입력 크기 제한을 적용한다.
- 문서는 악성코드 검사, MIME 확인, 크기 제한, 격리 저장 후 처리한다.
- 계약 후 인증·문서 보안은 리걸프렌즈의 보안 기준과 인계 계약에서 별도로 검증한다.
- 보존기간이 끝났거나 목적이 끝난 세션·임시 업로드·복구 토큰은 자동 삭제한다.

### 사례·AI

- 익명화는 “이름 삭제”가 아니라 조합에 의한 재식별 위험 평가까지 포함한다.
- 공개 사례 승인과 철회 흐름을 제공하고 철회 시 검색 캐시·파생 데이터까지 처리한다.
- AI 제공자·모델별 입력 보존·학습 사용·처리 지역·하위처리자를 기록한다.
- 민감도가 높은 자유 서술은 모델 입력 전 비식별화하고, 원문과 AI 출력의 접근 권한을
  분리한다.

## 14. 모바일·접근성·성능 기준

### 14-1. 모바일

- 360px 폭부터 본문과 핵심 행동이 가로 스크롤 없이 동작한다.
- 키보드가 열린 상태에서도 현재 질문·오류·다음 버튼이 보인다.
- 주소창·홈 인디케이터를 고려한 `safe-area` 여백을 둔다.
- 전화가 어려운 상황을 고려해 전화만 강요하지 않는다.
- 카메라 촬영 문서는 자동 자르기·재촬영·업로드 상태·실패 복구를 지원한다.
- 느린 4G와 중저가 Android 기기를 실제 시험 기준에 포함한다.

### 14-2. 접근성

- WCAG 2.2 AA를 출시 기준으로 삼는다.
- 모든 기능을 키보드로 사용할 수 있고 포커스 순서가 시각 순서와 일치해야 한다.
- 최소 터치 영역은 48×48px을 목표로 한다.
- 제목 구조, 랜드마크, 필드 라벨, 상태 메시지, 오류 요약을 보조기기가 이해하게 한다.
- 상담·진단의 제한시간이 있다면 연장하고, 인증 만료로 답을 잃지 않게 한다.
- PDF만 제공하지 말고 핵심 내용은 HTML로 함께 제공한다.
- 전화 외 텍스트 기반 도움과 장애가 있는 사용자의 대리·지원 절차를 설명한다.

### 14-3. 성능 예산

Google Core Web Vitals의 75백분위 기준을 최소선으로 삼고 내부 목표를 조금 더 엄격히 둔다.

| 지표 | 출시 기준 | 내부 목표 |
|---|---:|---:|
| LCP | 2.5초 이하 | 모바일 2.0초 이하 |
| INP | 200ms 이하 | 150ms 이하 |
| CLS | 0.1 이하 | 0.05 이하 |

- 공개 콘텐츠는 서버 렌더링·정적 재검증을 기본으로 하고 상호작용만 작은 client island로
  만든다.
- 첫 화면에 자가진단 전체 코드를 싣지 않고 시작 시 지연 로딩한다.
- 히어로는 실제 필요한 경우만 최적화된 AVIF/WebP를 사용한다.
- 한국어 글꼴은 필요한 굵기와 문자 범위를 최소화해 자체 호스팅한다.
- 공개 페이지에 세션 기반 `no-store`를 무조건 적용하지 않는다.
- 타사 스크립트는 목록·용량·목적·소유자를 관리하고 동의 전 불필요한 픽셀을 실행하지
  않는다.
- 스캐폴딩 후 모바일 공개 페이지의 초기 JavaScript 예산을 측정해 라우트별 상한을
  CI에서 관리한다.

## 15. 검색·AI 검색 설계

Google의 현재 가이드는 AI 검색만을 위한 별도 비법이나 특별한 AI 스키마보다 기존 검색의
기술 기반, 독창적이고 사람에게 유용한 콘텐츠, 접근 가능한 모바일 경험을 강조한다.
네이버도 수집 가능성, 고유 콘텐츠, 정확한 출처·구조를 기본으로 본다.

### 15-1. 콘텐츠 전략

초기 주제 묶음은 사용자의 말로 구성한다.

1. **지금 생긴 문제:** 독촉, 급여·계좌 압류, 지급명령, 경매
2. **제도 선택:** 개인회생 조건, 개인파산·면책 조건, 둘의 차이
3. **숫자:** 소득·채무·재산·부양가족·변제의 관계
4. **생활 영향:** 직장, 가족, 통장, 카드, 주거, 차량, 사업
5. **과정:** 기간, 법원 단계, 보정, 준비 서류, 기각·면책불허가 쟁점
6. **신뢰·계약:** 누가 맡는지, 상담 과정, 비용 구조, 정보 보호
7. **종결 이후:** 결정문 보관, 후속 행정, 신용 회복 관련 사실 확인

각 허브는 공식 설명, 로앤 변호사의 원본 해설, 승인된 익명 사례, 관련 질문을 연결한다.
검색 문구만 바꾼 대량 생성 페이지는 만들지 않는다.

### 15-2. 기술 SEO

- 공개 핵심 본문은 초기 HTML에 있고 JavaScript 상호작용 뒤에 숨기지 않는다.
- 모바일과 데스크톱의 핵심 본문·제목·구조화 데이터를 동일하게 유지한다.
- 사람이 읽는 URL, 유일한 title/H1, self-canonical, 올바른 상태 코드를 쓴다.
- `sitemap-pages.xml`, `sitemap-guides.xml`, `sitemap-cases.xml`을 만들고
  sitemap index로 묶는다.
- 네이버 서치어드바이저, Google Search Console, Bing Webmaster Tools를 연결한다.
- 콘텐츠 변경은 IndexNow와 사이트맵 `lastmod`로 알리되 정확한 변경 시각만 보낸다.
- 이전 URL은 301 지도와 회귀 테스트로 관리한다.
- 검색 결과에 노출할 이유가 없는 접수 상태, 폼 완료, 후기·사례 필터 조합은
  인증·`noindex`로 막는다. `robots.txt`를 보안 수단으로 사용하지 않는다.

### 15-3. 구조화 데이터

보이는 내용과 정확히 일치하는 경우에만 다음을 사용한다.

- `Organization` 또는 적합한 법률 서비스 조직 정보
- `WebSite`와 사이트명
- `BreadcrumbList`
- 해설 글의 `Article`
- 변호사 소개의 `ProfilePage`와 `Person`
- 실제 사무소 정보

구조화 데이터만 넣는다고 품질이나 AI 검색 노출이 보장되는 것은 아니다. FAQ 등은
검색 기능을 얻기 위한 마크업이 아니라 실제 사용자가 읽는 정보 구조로 유지한다.

### 15-4. AI 검색과 출처성

- 문서 첫 부분에 질문의 직접 답을 두고, 아래에서 예외·근거·상황을 설명한다.
- 조직명, 변호사명, 사무소, 연락처를 사이트와 외부 공식 프로필에서 일관되게 관리한다.
- 공식 법원·법령·대한변협 자료로 연결하고 검토일을 노출한다.
- 독창적인 사례·도표·질문 데이터처럼 로앤만 제공할 수 있는 정보를 만든다.
- 반복되는 상담 질문은 챗봇 안에만 가두지 않고 변호사가 검토한 공개 문서로 전환한다.
- `OAI-SearchBot`을 허용하면 ChatGPT 검색에서 요약·출처로 발견될 수 있다.
  모델 학습용 `GPTBot` 허용 여부는 별도 정책으로 정할 수 있다.
- ChatGPT 유입의 `utm_source=chatgpt.com`을 first-party 분석에서 구분한다.
- 네이버의 출처 설명 제한 메타 태그를 무심코 넣지 않는다.
- `llms.txt`, 특수 “GEO” 문구, 대량 AI 콘텐츠를 우선 과제로 두지 않는다.

### 15-5. 편집 운영

- 법령·법원 실무처럼 변동 가능성이 큰 문서는 90일 이내 검토 주기를 기본으로 한다.
- 일반 안내도 180일마다 소유자가 재검토한다.
- 중요한 변경이 있으면 본문 상단에 변경 요약과 적용일을 표시한다.
- AI 초안은 출처와 함께 콘텐츠 큐에 들어오고, 책임 변호사 승인 없이는 발행되지 않는다.
- 삭제보다 통합·갱신을 우선하며 변경 이력을 남긴다.

## 16. 측정과 개선

### 16-1. 북극성 지표

**적합한 해결 경로에 연결되고, 필요한 다음 행동을 이해해 완료한 고객의 비율**

단순 문의 수나 수임률만 최대화하면 불안을 자극하는 광고, 부적합한 문의, 상담자 과부하,
사후 불만을 키울 수 있다. 따라서 전환·운영 품질·고객 결과를 함께 본다.

### 16-2. 지표 체계

| 층 | 대표 지표 |
|---|---|
| 발견 | 색인된 유효 페이지, 비브랜드 유입, AI 검색·네이버·Google 출처별 유입 |
| 이해 | 핵심 답변 도달, 비교·가이드 이동, 반복 검색 감소, 유용성 피드백 |

### 16-3. 실험 원칙

- 버튼 색보다 질문 순서, 설명의 명료성, 입력 부담, 사람 인계 품질을 먼저 실험한다.
- 민감한 상황을 이용한 개인화나 숨겨진 기본 동의는 실험하지 않는다.
- 법률·비용·결과·사례 문구 실험은 사전 승인된 변형 안에서만 한다.
- 전환 상승과 함께 상담 품질·취소·불만·사건 적합성의 변화도 본다.
- 표본이 작거나 편향된 경우 승자를 단정하지 않고 보류한다.

## 17. 구축 순서

사용자에게 보일 홈페이지가 없는 현재 상태에서는 인프라와 내부 이벤트만 먼저 만드는
것보다, **검색 가능한 공개 기반과 상담 수직 흐름을 함께 세우는 것**이 우선이다.

### Phase 0 — 승인과 자산 정리

- 이 설계안 확정
- 정식 도메인 `lawandfirm.com` 유지
- 책임 변호사·광고 심사 절차 확정
- 현재 사이트 URL·콘텐츠·검색·전환 자산 인벤토리와 검색의도별 랜딩페이지 맵
- 기존 고객후기 전량 추출·PII 점검·이관 검증
- 공개 사례 동의·익명화·승인 정책
- 실제 변호사·사무소·사진·운영 SLA 자료 수집

### Phase 1 — 홈페이지 기반

- 모노레포와 `apps/homepage`, 공용 UI·콘텐츠 모델 스캐폴딩
- 디자인 토큰·접근 가능한 헤더·푸터·본문 템플릿
- `/bank` 홈, 개인회생 신청자격 랜딩, 후기 허브, 회생, 파산, 비교, 절차, 서류,
  FAQ, 로앤·변호사 페이지
- CMS 또는 Git 기반 검토·승인 워크플로
- robots, sitemap, metadata, 구조화 데이터, 분석·동의 기반
- 현재 URL 301 테스트

### Phase 2 — 첫 번째 끝까지 연결된 흐름

- 광고·검색 유입 → 익명 상황 정리 → 상담 요청
- gateway → ERP 상담 등록 → 담당자 배정·연락 상태
- AdPilot 가명 attribution과 전환 환류
- 접수 완료·상태 확인·중복 제출 방지
- 내부 상담 요약·누락 질문 제안

### Phase 3 — 사례·탐색

- 리걸프렌즈와 분리된 공개 사례 승인 파이프라인
- 익명화·범주화·철회·검토 이력
- 사례 필터와 관련 사례 이유 설명
- 상담 결과에서 관련 가이드·사례 연결

### Phase 4 — 리걸프렌즈 인계 고도화

- 계약 상태 기반 리걸프렌즈 초대·재발송·지원 흐름
- ERP·리걸플로·리걸프렌즈 상태 어댑터와 중복 방지
- 홈페이지의 계약 고객 이동 안내와 인계 실패 모니터링
- 자체 고객 포털은 검증된 별도 요구가 생길 때만 재평가

### Phase 5 — 내부 AI·사후관리·최적화

- STT·상담 코파일럿과 검토 가능한 요약
- 문서 분류·보완 감지
- 종결 유형별 체크인·회복 정보
- 콘텐츠 변경 감지와 변호사 검토 큐
- AdPilot의 사건 품질·수납 기반 폐쇄루프 개선

### 첫 출시의 완료 조건

- 모바일에서 정보 탐색부터 상담 접수까지 키보드·스크린리더로 완료 가능
- 기존 핵심 URL의 보존 또는 단일 301 검증
- 공개 핵심 문서에 작성자·검토자·근거·검토일 표시
- 상담 데이터가 중복 없이 ERP에 생성되고 상태가 추적됨
- 광고 유입과 상담·연락 단계가 개인정보 원문 없이 연결됨
- 공개 사례가 승인된 별도 데이터셋에서만 노출됨
- 광고·개인정보·AI 출시 체크리스트를 책임자가 승인
- CWV·오류·접수 성공·동의·안전 지표 대시보드가 준비됨

## 18. 구현 전에 확정할 의사결정

1. **정식 도메인:** 기존 `lawandfirm.com` 유지로 확정했다.
2. **광고 규정 검토:** 상황 정리·계산 도구의 공개 가능 범위, 명칭·출력, AI 연결 범위를
   책임 변호사와 확인한다.
3. **표시 책임자:** 홈페이지 전체 광고 책임 변호사와 콘텐츠별 검토자를 정한다.
4. **운영 약속:** 연락 가능한 시간, 상담 채널, 사무소, 비용 설명 범위를 실제 운영과
   일치시킨다.
5. **공개 사례:** 사용 가능한 사건 범위, 동의·익명화·철회·최소 집단 기준을 승인한다.
6. **콘텐츠 시스템:** Git 기반 검토형 콘텐츠와 별도 CMS 중 운영자가 실제 관리할 방식을
   정한다.
7. **고객 접점 경계:** 홈페이지 회원가입·자체 포털은 후순위이며 계약 후 사건 공유는
   리걸프렌즈가 담당한다.
8. **분석 도구:** first-party 이벤트를 기본으로 하고 꼭 필요한 외부 도구와 데이터
   보유기간을 확정한다.
