# 센트릭스 A타입 클릭투콜·통화 결과 v1

## 범위

ERP 상담 상세에서 현재 담당자가 `센트릭스로 전화`를 누르면 LG U+ 고급형 센트릭스
개인 전화기에 먼저 벨이 울리고, 직원이 수화기를 들었을 때 고객 번호로 연결한다.
이 기능은 소프트폰이나 PC 음성 스트리밍이 아니다. 음성 입출력은 기존 센트릭스
전화기를 사용한다.

기준 규격은 로컬 `Centrex_Rest_API_v4.3.pdf`의 A타입 REST API다. B타입은 새 구현
범위에서 제외한다.

## 처리 흐름

1. ERP 브라우저는 고객 전화번호가 아니라 상담 ID만 same-origin API로 보낸다.
2. gateway는 로그인 직원이 해당 상담의 현재 담당자인지, 전화번호가 있는지, 활성
   개인 회선이 연결되어 있는지 확인한다.
3. `telephony.call.requested` outbox 이벤트와 `telephony_calls` 원장을 한 트랜잭션으로
   만든다. 이벤트에는 통화·상담·회선 참조만 있고 고객 번호는 없다.
4. 전용 워커가 한 번에 하나씩 명령을 선점하고, 저장된 상담 전화번호를 발신 직전에만
   복호화해 `POST https://centrex.uplus.co.kr/RestApi/clickdial`로 보낸다.
5. ERP는 `queued → dispatching → succeeded | failed | unknown` 명령 상태를 조회한다.
6. 명령 전달이 성공하면 같은 워커가 A타입 `callhistory`의 발신 이력을 조회해 회선,
   마스킹된 고객 번호, 요청 시각을 대조한다. 한 이력은 한 ERP 발신 건에만 연결한다.
7. 통화가 끝난 이력을 찾으면 센트릭스 상태와 시작·종료시각, 전체 시간, 연결 시간,
   호출 시간을 원장에 보존한다.
8. ERP가 종료를 감지하면 결과 창을 자동으로 열고 담당자가 `고객과 상담함`,
   `음성사서함 연결`, `받지 않음`, `수신 거절`, `통화 중`, `발신 취소` 중 실제 상황을
   확정하거나 `재상담 필요`로 분류한다. 확정값과 직원·시각은 통화 원장과 감사 원장에
   함께 남는다.

LG U+ 규격상 클릭투콜 응답은 자신의 전화기에 먼저 울린 벨을 받은 뒤에 반환된다.
따라서 `dispatching`일 때 수화기를 들고, `succeeded`는 고객 연결 명령이 정상적으로
이어졌다는 뜻이다. 고객에게 실제 연결됐는지는 후속 `callhistory`로 판단한다.

단, 센트릭스 이력만으로 사람과 음성사서함, 통화 중과 수신 전 발신 취소를 항상 구분할
수는 없다. 로컬 통제 시험에서는 아래처럼 관찰됐다.

| 실제 상황 | 센트릭스 상태 | 전체/연결 | ERP 자동 판정 범위 |
|---|---:|---:|---|
| 발신자가 수신 전에 끊음 | `FAIL` | 0초/0초 | 미연결 |
| 고객과 통화 | `OK` | 22초/16초 | 연결 |
| 무응답 후 음성사서함 | `OK` | 56초/10초 | 연결 |
| 수신 거절 후 음성사서함 | `OK` | 17초/8초 | 연결 |
| 상대 회선 통화 중 | `FAIL` | 0초/0초 | 미연결 |

그래서 ERP는 연결·미연결과 시간은 자동 기록하되, 실제 업무 결과는 담당자가 확정한다.
상담 목록은 상담별 최신 확정 통화 결과가 `받지 않음`이면 `부재`, `재상담 필요`이면
같은 이름의 배지를 표시한다. 두 상태는 `확인 필요` 지표와 작업 큐에 포함되며, 이후 더
최신 통화 결과를 확정하면 최신 결과 기준으로 목록에서 해소된다.

## OpenAPI 발신 관측과 전화데스크 중복 제거

ERP 클릭투콜은 REST 명령과 별개로 Windows OpenAPI bridge에서 실제 발신 통화로 다시
관측될 수 있다. 두 원장은 서로 다른 사실을 보존하므로 합치지 않고
`telephony_call_observation_links`로만 1:1 연결한다. 같은 endpoint·상대번호 HMAC 지문,
요청 대비 -5초~+120초의 관측 시작 조건 안에서 가장 가까운 미연결 명령을 연결한다.
마이그레이션 전 기존 원장의 일괄 backfill은 양쪽 상호 최근접인 조합만 허용한다.
연결된 명령과 관측은 통합 전화데스크에서 한 행으로 표시하고, 연결되지 않은 OpenAPI
발신은 `센트릭스 직접 발신`으로 표시한다. 이 연결은 새로운 전화를 만들거나 REST 명령을
재실행하지 않으며 기존 원장의 상태를 덮어쓰지 않는다.

2026-08-06 migration `0032`와 gateway·ERP 릴리스 `20260806T072225Z-phone-desk`를 운영에
배포했다. 배포 시점의 운영 클릭투콜 명령과 관측 발신은 모두 0건이어서 과거 연결은
생기지 않았다. 페이지·목록 API·SSE 인증 canary는 통과했으며 실제 운영 클릭투콜과 물리
전화기 발신 중복 제거는 사용자가 사무실에 복귀한 뒤 확인한다. 같은 날 사용자의 명시적
승인으로 현재 자격증명을 `userinfo`에 다시 검증하고 운영 gateway secret에 SHA-512만
저장해 워커를 활성화했다. 활성화 전후 클릭투콜 명령·대기 이벤트·전송 시도는 모두
0건이어서 실제 발신은 없었다. 운영 컨테이너의 `userinfo`도 HTTP 200과 회선·내선 일치를
반환했다. 사용자가 센트릭스 비밀번호를 변경하면 다음 발신 전에 secret의 SHA-512 값도
반드시 함께 갱신한다. 2026-08-07부터는 직원관리의 `회선 테스트 및 저장`이 이 갱신을
대신한다. 관리자가 전체 회선번호·내선·해당 계정의 현재 비밀번호를 입력하면 `userinfo`
일치 검증 뒤 직원 주 회선과 인증값을 한 트랜잭션으로 반영한다.

## 회선과 자격증명

`telephony_endpoints`는 아래 값을 분리해 저장한다.

- 실제 070 회선과 내선
- 센트릭스 API 로그인 ID
- 운영 비밀 맵을 찾는 `credential_key`
- 직원과 회선을 연결하는 활성·주 회선 바인딩

비밀번호 원문은 브라우저의 현재 제출과 gateway 프로세스 메모리에서만 다루며 DB·환경
파일·Secrets Manager·감사 로그에 저장하지 않는다. gateway는 입력 즉시 SHA-512로
변환해 `userinfo`를 호출하고, 반환된 전체 회선번호와 내선이 입력값과 모두 같을 때만
인증값을 저장한다. SHA-512 역시 비밀번호와 같은 운영 비밀로 취급한다.

신규 직원별 인증값은 전용 `telephony_endpoint_credentials`에 AES-256-GCM으로 암호화해
저장한다. 암호화 AAD는 endpoint ID에 묶고, 암호문·12바이트 nonce·키 버전·검증 직원과
시각만 보존한다. `lawand_app`만 이 테이블을 읽고 갱신할 수 있으며 `lawand_viewer`와
`PUBLIC`에는 SELECT도 주지 않는다. 기존 `office-main-4591` 운영 자격증명은 무중단
전환을 위한 읽기 전용 Secrets Manager fallback으로 유지하고, 같은 endpoint에 DB
인증값이 생기면 DB 값을 우선한다.

```text
LAWAND_CENTREX_CREDENTIALS_JSON={"<credential-key>":"<sha512-128-hex>"}
LAWAND_CENTREX_WORKER_ENABLED=true
```

직원관리 화면의 저장은 먼저 `userinfo`를 호출해 API 계정의 실제 070 번호와 내선이
입력값과 완전히 같은 경우에만 endpoint 생성·인증값 암호화 저장·직원 주 회선 배정을
반영한다. 회선번호가 센트릭스 API 로그인 ID이며, 비밀번호는 저장할 때마다 다시 입력한다.
기존 운영 자동화나 장애 복구에서는 아래 연결 명령을 보조 수단으로 유지한다.

```bash
corepack pnpm --filter @lawand/gateway centrex:link -- \
  --staff-email '<staff-email>' \
  --label '<phone-label>' \
  --line-number '<070-number>' \
  --extension '<extension>' \
  --api-login-id '<centrex-api-login-id>' \
  --credential-key '<credential-key>'
```

2026-08-05 처음 전달받은 로그인은 요청 회선과 다른 회선을 반환했지만, 이후 정정된
API 로그인은 `userinfo`에서 요청한 실제 회선·내선과 정확히 일치했다. 로컬 활성 직원의
주 회선 연결까지 완료했으며 비밀번호 원문과 SHA-512 값은 파일·DB에 저장하지 않았다.
로컬에서는 대화형 프로세스 메모리에만 비밀을 넣어 워커를 활성화했고, 사용자 통제 아래
실제 발신 5건과 사후 이력 대사를 확인했다. 파일·DB에는 비밀번호 원문이나 해시를 남기지
않았다. 2026-08-07 이전 운영은 비밀번호 원문 없이 AWS Secrets Manager의 SHA-512 비밀
맵만 사용했고, 이후 직원관리에서 검증한 endpoint는 전용 DB 암호문을 우선 사용한다.

## 실패와 중복 발신 기준

- 같은 상담·직원이 30초 안에 다시 누르면 진행 중인 통화 요청을 재사용한다.
- 발신 명령이 성공했지만 통화 이력 대사가 끝나지 않은 건도 재사용해 중복 전화를 막는다.
- 인증·권한·요청 오류는 `failed`로 끝내며 자동 재시도하지 않는다.
- timeout, 응답 해석 실패, 워커 중단처럼 명령 수행 여부가 불명확하면 `unknown`으로
  끝내고 자동 재시도하지 않는다. 직원이 전화기 상태를 먼저 확인해야 한다.
- 센트릭스 명령은 전역 직렬 처리하고 명령 사이에 최소 3초를 둔다.
- URL과 로그에는 API 자격증명이나 고객 전화번호를 남기지 않는다.
