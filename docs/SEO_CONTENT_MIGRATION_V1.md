## 1. 이번 단계의 목표

새 사이트의 본문은 기존 홈페이지를 복사하지 않고 공식 1차 자료와 로앤의 원본 해설로
다시 만든다. 기존 사이트에서는 필수 자산인 고객후기와 주제 누락 확인에 필요한 참고만
가져온다. 광고 키워드마다 같은 상담 폼을 복제하는 대신, **검색한 질문에 가장 먼저
정확히 답하는 랜딩페이지**를 만든다.

Phase 0의 완료 조건은 다음과 같다.

1. `/bank` 홈페이지와 검색의도별 신규 콘텐츠를 먼저 구현한다.
2. 기존 개인회생·파산 고객후기를 전량 이관 가능한 원천 데이터로 확보한다.
3. 내부 사건이 공개 사례 후보가 된 뒤 발행되기까지 승인 흐름을 확정한다.
4. 첫 구현 페이지의 검색의도, 직접 답변, 근거, 내부 링크, 전환 행동을 문서화한다.
5. 출시 전 검색 유입·외부 링크가 있는 기존 핵심 URL만 유지·301 여부를 확인한다.

## 2. 2026-07-25 기준 기존 사이트 관찰

### 확인된 자산

- 개인회생·파산 허브: `/bank/`
- 개인회생: 제도, 장점, 신청자격, 절차, 필요서류, 변제 관련 페이지
- 개인파산·면책: 제도, 신청자격, 절차, 필요서류 페이지

- FAQ, 상담 게시판, 판례, 서식, 성공사례, 고객후기
- 서울·대전·부산 사무소와 전화·주소 정보

### 기술·이전 위험

- `/sitemap.xml`과 `/wp-sitemap.xml`이 확인되지 않아 메뉴·게시판·검색 색인을 함께
  조사해야 한다.
- 공개 페이지가 세션 쿠키와 `no-store/no-cache` 응답을 사용한다.
- 후기 일부는 `?kboard_content_redirect={id}` 또는
  `/successioncase_epilogue/?mod=document&uid={id}`처럼 복수 쿼리형 주소로 색인됐다.
- 고객후기 게시판은 관찰 시점에 마지막 페이지가 337이고, 페이지당 10개·마지막 페이지
  1개로 보여 **약 3,361개**다. 운영 중인 동적 데이터이므로 DB 추출 시 최종 개수를
  다시 확정한다.
- 오래된 FAQ·상담 답변에는 현재 법령·법원 실무와 다를 수 있는 수치·기간·표현이 있어
  검토 없이 복사하지 않는다.

## 3. 새 콘텐츠 우선과 최소 URL 보호

### 필요한 입력

- WordPress 페이지·게시물 export는 주제 누락 확인용 선택 자료
- KBoard 고객후기·사례·FAQ·상담 게시판의 DB export
- Google Search Console의 최근 16개월 상위 page/query/click/impression/CTR/position
- 네이버 서치어드바이저의 수집·색인·유입 데이터
- 웹 분석의 landing page·상담 전환 데이터
- 외부 링크 목록과 현재 access log

HTML 크롤링과 WordPress export는 새 본문의 원천으로 사용하지 않는다. 고객후기는
페이지네이션·비공개 필드·수정 이력을 놓치지 않도록 **KBoard DB export를 이관 원천**으로
삼는다.

### 핵심 URL 보호 목록 필드

| 필드 | 설명 |
|---|---|
| `legacy_url` | 쿼리를 포함한 기존 발견 URL |
| `canonical_seen` | 기존 페이지가 표시하는 canonical |
| `content_type` | page, faq, review, case, consultation 등 |
| `http_status`, `indexable` | 현재 응답과 색인 가능 여부 |
| `title`, `h1`, `last_modified` | 현재 검색·편집 정보 |
| `gsc_clicks`, `impressions`, `top_queries` | 검색 자산 판단 |
| `backlinks`, `conversions` | 외부 가치와 실제 전환 |
| `legal_review_state` | 재사용 전 법률 검토 필요 수준 |
| `decision` | keep, rewrite, merge, redirect, retire |
| `target_url` | 새 canonical URL |
| `redirect_tested` | 단일 301·최종 200 검증 상태 |

### 이전 규칙

1. 순위가 있는 URL이라고 낡은 본문을 그대로 복사하지 않는다. **검색의도만 보존하고
   본문은 현재 공식 기준으로 다시 쓴다.**
2. 실제 검색 유입이나 외부 링크가 있는 핵심 URL만 보호 목록에 넣는다.
3. 가장 가까운 새 문서로 한 번만 301하고, 홈으로 무더기 리다이렉트하지 않는다.
4. 새 페이지의 제목·H1·본문·canonical·내부 링크·사이트맵·구조화 데이터를 검증한다.
5. 이 작업은 첫 화면과 신규 랜딩 구현을 막지 않으며 출시 전에 완료한다.

## 4. 검색의도별 랜딩페이지 원칙

광고 그룹과 랜딩페이지는 **키워드 문자열**이 아니라 사용자가 해결하려는 **하나의
질문**으로 연결한다. 같은 답을 하는 문서를 지역명·어순만 바꿔 대량 생성하지 않는다.
Google은 유사 검색어만 겨냥한 doorway page와 검색 조작 목적의 대량 콘텐츠를 스팸으로
본다.

모든 핵심 랜딩은 다음 순서를 따른다.

1. 검색 질문에 대한 3~5문장의 직접 답변
2. 적용 범위와 기준일
3. 기본 요건과 사용자가 자주 놓치는 예외
4. 스스로 확인할 체크리스트
5. 공식 법원·법령 근거
6. 변호사가 승인한 관련 실제 사례
7. 해당 맥락과 관련된 고객후기
8. 다음 읽을 문서와 사람 상담 요청
9. 작성자·검토 변호사·최초 작성일·최근 검토일·변경 이력

CTA는 `가능/불가능 판정`이나 결과를 암시하지 않고 `내 상황에서 확인할 쟁점 정리`,
`변호사에게 상담 요청`처럼 다음 행동을 정확히 설명한다.

2026-07-26에 `/bank/personal-rehabilitation`, `/bank/personal-bankruptcy`,
`/bank/situations` 카테고리 허브를 구현했다. 기존 상세 canonical은 유지하고, 메뉴와
breadcrumb·구조화 데이터에서 각 허브를 실제 상위 페이지로 연결했다. 상황별 페이지는
긴급 문제·채무 원인·직업과 소득으로 표시하되 URL 디렉터리를 추가로 나누지 않는다.
고객후기·사례는 실제 데이터 이관과 승인 파이프라인 전에 빈 허브를 만들지 않고 현재
홈 섹션으로 연결한다.

`개인회생 신청자격`을 첫 검색 랜딩 구현 대상으로 삼는다. 기존
`/bank/revival_qualificationtoapplyrevival/`의 검색 성과를 확인한 뒤 같은 URL 유지 또는
새 canonical로 단일 301한다.

2026-07-26에 신규 canonical
`/bank/personal-rehabilitation/eligibility`의 모바일 우선 초안을 구현했다. 소득·채무
한도·현재의 변제 곤란 상태·최근 면책 이력을 직접 답변과 체크리스트, FAQ, 공식 근거로
구성했다. 기존 URL의 실제 검색 성과 확인과 단일 301 결정, 책임 변호사 검토는 출시
게이트로 남아 있다.

2026-07-26에 `/bank/compare` 모바일 우선 초안도 구현했다. 소득 유무만으로 두 제도를
가르는 오해를 피하고 신청 상태·변제 재원·소득·재산·채무 한도·면책 절차를 같은
구조에서 비교했다. 개인회생 신청자격 페이지와 `/bank` 허브의 관련 링크를 신규
canonical로 연결했으며, 자동 추천이나 감면 결과 암시는 넣지 않았다. 출시 전 책임
변호사의 법률·광고 카피 검토는 별도 게이트로 유지한다.

같은 날 `/bank/personal-rehabilitation/process` 모바일 우선 초안도 구현했다. 신청
준비부터 법원 심사·개시·채권 확인·인가·변제·면책까지의 흐름을 단계별로 설명하고,
법정 기한과 실제 소요기간을 구분해 보정·송달·이의 등 기간 변수를 안내한다.

같은 날 `/bank/personal-bankruptcy/eligibility` 모바일 우선 초안도 구현했다.
지급불능을 소득 유무나 부채초과 하나로 자동 판정하지 않고 재산·신용·소득·생계비와
변제 가능성을 함께 설명했다. 파산선고와 면책심사를 분리하고 면책불허가 사유,
비면책채권, 과거 면책 기간을 FAQ와 공식 근거에 연결했다.

같은 날 `/bank/personal-rehabilitation/documents` 모바일 우선 초안도 구현했다.
법률상 기본 첨부서류와 직업·재산·가족 상황에 따른 증빙을 분리하고, 신청서·채권자목록·
재산목록·소득 및 지출 목록·소득 증빙·진술서·변제계획안이 서로 맞아야 한다는 준비
원칙을 설명했다. 관할 법원과 사건에 따라 추가 자료가 달라질 수 있음을 명시하고
최신 양식 확인, 보정기한과 민감정보 전송 주의까지 한 흐름으로 연결했다.

같은 날 `/bank/personal-rehabilitation/repayment` 모바일 우선 초안도 구현했다.
개인회생 변제금을 채무액의 고정 비율이나 단순 계산값으로 제시하지 않고, 현행
채무자회생법상 예상 소득·법정 공제·법원이 정하는 생계비·필요한 영업비용으로 구성되는
가용소득을 출발점으로 설명했다. 청산가치 보장, 변제기간, 우선권 있는 채권과 수행
가능성을 함께 확인하고 급여·사업·부양·주거비·의료비·재산 등 상황별 산정 근거를
연결했다. 결정형 계산 도구는 책임 변호사의 광고 규정 검토 전까지 공개하지 않는다.

같은 날 `/bank/personal-bankruptcy/process` 모바일 우선 초안도 구현했다.
파산·면책 동시신청, 법원 심사와 보정·예납, 파산선고와 관재인 선임, 재산·채무 조사,
환가·배당 후 종결 또는 재산 부족 등에 따른 폐지, 별도의 면책심사와 결정 확정까지를
일곱 단계로 설명했다. 전체 완료기간을 단정하지 않고 보정·예납, 최근 거래 조사,
재산 환가와 채권자 이의가 기간에 미치는 영향을 구분했다. 파산선고·파산절차
종결/폐지·면책허가결정의 효력 차이와 신청만으로 독촉·압류가 모두 자동 중지되지
않는다는 경계도 함께 안내했다.

같은 날 `/bank/personal-bankruptcy/documents` 모바일 우선 초안도 구현했다.
현행 법률·대법원규칙과 개인파산·면책 사건 처리 예규의 여섯 표준양식을 기준으로
신청서·진술서·채권자목록·재산목록·현재 생활상황·수입 및 지출 목록을 설명했다.
신분·주거, 소득·사업, 계좌·보험·증권·가상자산, 부동산·차량, 채무·소송과 최근
거래를 상황별 소명자료로 나누고, 법원별 목록과 보정·관재인 추가 요구가 달라질 수
있다는 점과 민감정보 전송 주의를 함께 안내했다.

같은 날 `/bank/situations/collection-and-seizure` 모바일 우선 초안도 구현했다.
일반 추심 연락, 지급명령, 소장·조정 문서, 가압류, 통장·급여 압류와 경매·체납처분을
문서별로 구분하고 송달일·사건번호·대상 채권과 재산을 먼저 확인하도록 구성했다.
지급명령의 2주 이의기간을 다른 문서에 일반화하지 않았고, 채권추심법·
개인채무자보호법상 연락 제한과 민사집행법상 압류금지채권·생계비계좌를 구분해
안내했다. 개인회생 신청과 중지·금지명령·개시결정, 개인파산 신청과 파산선고의
효력이 서로 같지 않다는 경계도 함께 반영했다.

같은 날 `/bank/situations/investment-debt` 모바일 우선 초안도 구현했다.
주식·가상자산 투자 채무라는 원인 하나로 개인회생·개인파산 가능 여부를 단정하지 않고,
현재 소득·전체 채무와 차입 → 투자 → 매도·출금 → 남은 자산의 흐름을 확인하도록
구성했다. 개인회생의 일반 요건과 청산가치, 서울회생법원 실무준칙 제408호의 적용 범위,
개인파산의 투기적 거래 관련 면책불허가 쟁점과 재량면책을 구분했다. 실무준칙을 전국
공통의 자동 감면 기준으로 쓰지 않았고, 증권·거래소·개인지갑 자료와 개인정보·개인키
보호 원칙을 함께 안내했다.

같은 날 `/bank/situations/self-employed` 모바일 우선 초안도 구현했다.
자영업자의 매출액을 곧바로 개인회생 소득이나 변제금으로 보지 않고, 계속적·반복적인
영업소득 가능성, 월별 전체 매출에서 실제 필요한 영업비용을 구분한 순소득, 사업재산과
변제계획 수행 가능성을 함께 확인하도록 구성했다. 세무신고·카드·플랫폼 정산·사업계좌와
실제 비용을 대조하고, 사업 유지·신규 개업·폐업·가족 공동운영에 따라 달라지는 자료와
설명을 안내했다. 서울회생법원의 최근 1년 산정 실무를 전국 공통의 고정 제출기간이나
업종별 고정 경비율로 일반화하지 않았고 사업자료의 개인정보 보호 원칙도 반영했다.

## 5. 고객후기 전량 이관

고객후기는 새 사이트의 필수 자산이다. 다만 “전량 이관”은 원문을 잃지 않고 시스템에
가져온다는 뜻이며, 개인정보나 공개하면 안 되는 내용까지 검수 없이 재노출한다는 뜻은
아니다.

### 이관 필드

- `legacy_id`, 원본 게시판·원본 URL
- 원문, 줄바꿈, 작성일, 마지막 수정일
- 기존 익명 작성자 표기
- 개인회생·개인파산 등 분야
- 상담·개시결정·인가결정·면책결정 등 작성 당시 단계
- 기존 키워드 태그
- 공개/삭제/수정 상태
- 원본 해시, 이관 시각, 이관 배치
- 개인정보 점검 상태, 광고 검토 상태, 공개 승인 상태

전화번호·이메일·IP·비밀번호 같은 검증용 원본은 공개 콘텐츠 모델에 넣지 않는다.
정말 보존이 필요한 검증 정보는 접근이 제한된 별도 저장소와 보존기간을 사용한다.

### 이관 절차

```text
KBoard DB export
  → 원본 불변 보관 + 행 수/해시 기록
  → 필드 정규화
  → 전화·계좌·주소·사건번호 등 PII 탐지
  → 중복·삭제·비공개 상태 확인
  → 운영자 검수 큐
  → 새 후기 저장소
  → 원본 대비 개수·샘플·해시 검증
  → 공개 페이지와 legacy 301 검증
```

### 공개 UX·SEO

- 원문을 임의로 미화하지 않고 오탈자까지 보존한다. 명백한 PII 제거가 필요하면
  `[개인정보 비공개]`처럼 편집 사실을 표시한다.
- 작성 당시 절차 단계와 작성일을 함께 보여 미래 결과 보장처럼 읽히지 않게 한다.
- 결과는 개인별 사실관계·법원·시점에 따라 다를 수 있음을 가까운 문맥에서 설명한다.
- 후기 목록은 분야·진행단계·시기별로 탐색하되, 필터 조합 URL은 기본적으로 색인시키지
  않는다.
- 짧은 후기마다 무조건 색인 페이지를 3천 개 이상 만들지 않는다. 기존 URL의 검색
  성과·외부 링크·원문 길이를 보고 고유 페이지 유지와 목록 내 위치로의 301을 결정한다.
- 로앤이 자사 후기를 통제하는 구조이므로 `Review`·`AggregateRating` 별점 리치결과를
  얻기 위한 자기서빙 구조화 데이터는 사용하지 않는다. 본문은 사용자가 읽을 수 있게
  그대로 제공하고 조직·페이지 정보만 정확히 마크업한다.
- 후기 삭제·정정 요청 경로와 처리 이력을 유지한다.

### 2026-07-29 실제 이관 결과

- 원천: Cafe24 MariaDB의 `wp_kboard_board_content`, `board_id=22`,
  `thumbnail_file=회생파산` 3,403건
- 공개: 3,359건
- 원본 삭제 상태로 공개 제외: 43건
- 콘텐츠 내 개인정보 패턴 검수 대기: 1건
- 분야: 개인회생 3,154건, 파산·면책 205건
- 기간: 2016년부터 2026년까지

MariaDB 10.1과 호환되는 Base64 행 스트림으로 원문 줄바꿈·한글·특수문자를 보존한다.
`wp_epilogueaddinfos`는 `main_id`별 최신 행 하나만 결합해 8개 경험 키워드를 가져온다.
원본 비밀번호·전화번호와 추가정보의 전화번호·성별·나이·유입경로는 SELECT 목록에서부터
제외한다. 새 DB는 이관 배치의 행 수·SHA-256과 후기별 원본 해시를 저장한다.

`scripts/import-legacy-reviews.mjs`는 읽기 전용 SELECT 뒤 새 PostgreSQL에 트랜잭션으로
upsert한다. 재실행 시 원본 해시가 같으면 사람이 완료한 개인정보 검수 상태를 보존하고,
원문이나 공개 상태가 바뀐 행만 자동 판정을 다시 적용한다. 원본 접속 비밀번호는
TTY 또는 일회성 환경변수로만 받고 Git 제외 파일에도 자동 저장하지 않는다.

`/bank/reviews`는 분야·작성 당시 단계·경험 키워드 탐색, 최신순 9건 페이지네이션,
긴 후기 네이티브 펼침, 원문·맥락·결과 비보장 원칙을 제공한다. 필터 조합은
`noindex, follow`이고 기존 `/bank/successioncase_epilogue`는 허브로 308/영구 이동한다.
개별 legacy UID의 검색 성과를 받은 뒤 상세 유지 또는 목록 위치 연결은 후속으로 확정한다.

## 6. 내부 사건의 지속적 공개 사례 파이프라인

실제 사건 요약은 일회성 마이그레이션이 아니라 계속 작동하는 편집 파이프라인으로 만든다.
자동화는 후보 추출·비식별 초안·분류·중복 탐지·발행 작업을 돕고, **공개 승인은 사람이
한다.**

```text
ERP 사건 단계 이벤트
  → 공개 후보 규칙
  → 최소 필드만 별도 작업공간으로 복사
  → 동의·공개 근거 확인
  → PII 제거·희귀 조합 범주화
  → AI 초안과 관련 공식 근거 후보
  → 재식별·중복·광고 표현 검사
  → 개인정보 담당 검수
  → 책임 변호사 법률·광고 검토
  → 예약 발행
  → sitemap lastmod·IndexNow·내부 링크 갱신
  → 정기 재검토·철회 처리
```

### 사례 콘텐츠 모델

- 출발 상황과 고객이 실제로 궁금해한 질문
- 넓은 구간으로 범주화한 소득·채무·재산·가구
- 핵심 쟁점과 확인한 자료
- 선택한 절차와 주요 진행 단계
- 공개 가능한 결과와 결정 시기
- 다른 사건에서 달라질 수 있는 핵심 조건
- 공식 근거, 작성자, 검토 변호사, 검토일
- 동의/법적 근거, 익명화 버전, 승인·철회 이력

성과 숫자만 다른 유사 사례를 반복 발행하지 않는다. 새로운 쟁점·직업·재산 구조·법원
실무·고객 질문 중 적어도 하나에 고유한 학습 가치가 있을 때 발행한다. AI가 작성한
초안은 검토 없이 자동 게시하지 않는다.

## 7. 계약 전환과 리걸프렌즈 인계

초기 홈페이지에는 회원가입과 자체 고객 포털을 두지 않는다.

```text
검색/광고 → 랜딩 → 정보·후기·사례 → 상담 요청
  → gateway → ERP 상담/계약 상태
  → 계약 확인 → 리걸프렌즈 초대·사건 정보 공유
```

- 익명 정보 탐색에 계정을 요구하지 않는다.
- 상담 요청은 최소 연락 정보와 별도 동의만 받는다.
- 접수 완료는 접수번호와 실제 연락 범위를 보여주고 회원가입을 강요하지 않는다.
- 계약 후 사건 정보·할 일·서류·상태는 리걸프렌즈에서 제공한다.
- 홈페이지에는 리걸프렌즈로 이동하는 명확한 링크와 지원 연락처만 둔다.
- 리걸프렌즈로 해결되지 않는 요구가 실제 데이터로 확인될 때만 홈페이지 포털을 재검토한다.

- `artifacts/content/reviews-source.ndjson`
- `artifacts/content/redirect-map.csv`
- `artifacts/content/inventory-report.md`

`artifacts/content`의 원본·PII 포함 파일은 Git에 커밋하지 않는다. 스키마·샘플·검증
리포트만 익명화해 커밋한다.

### 0C. 첫 콘텐츠 브리프

4. 개인파산 신청자격
5. 개인회생 필요서류

분석 이벤트와 상담 CTA까지 함께 완성한다.
